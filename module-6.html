01 / THINK → ACT → CHECK

Give the routine a state

A state tells you which part of the mission is active. WAIT, DRIVE, and DONE are easier to reason about than several unrelated booleans. Only one of these states is active at a time.

enum State { WAIT, DRIVE, DONE }
State state = State.WAIT;

02 / THINK → ACT → CHECK

Take one small update at a time

A control update reads inputs, chooses a transition, and sets an output. Avoid a blocking loop that prevents new readings from being processed. The lab advances one simulated second with each button press.

switch (state) {
    case WAIT:
        if (pathClear) state = State.DRIVE;
        break;
    case DRIVE:
        if (!pathClear || driveSteps >= 3) state = State.DONE;
        break;
    case DONE:
        break;
}
boolean motorOn = state == State.DRIVE;

03 / THINK → ACT → CHECK

Make time and reset explicit

In real code, measure elapsed time rather than assuming every update takes a second. System.nanoTime differences are useful for elapsed durations. DONE should stay stopped until an intentional reset; otherwise a clear reading might restart the mission unexpectedly.

long startNanos = System.nanoTime();
// On a later update:
double elapsedSeconds = (System.nanoTime() - startNanos) / 1_000_000_000.0;

04 / PREDICT → TEST

Your practice bench

Automation state lab

Step through one reading at a time. Each step represents 1 second. In WAIT, a clear path starts DRIVE. In DRIVE, a blocked path or 3 drive steps stops the robot. DONE stays stopped until reset.

Predict the result before running.

Results will appear here.
  1. Select blocked and step once. Why does it remain in WAIT?
  2. Select clear, step into DRIVE, then select blocked and step again.
  3. Reset and keep clear. Count the drive steps until DONE. Try stepping again.
