MODULE 07 / BUILD · TEST · EXPLAIN

Debug Like a Builder

I can compare expected and actual behavior and use a boundary test to justify a correction.

Use a browser and a prediction notebook. Java snippets are learning fragments unless labeled as complete programs. The labs run JavaScript models, not Java.

In this mission

1. Write the expectation first2. Test the boundary3. Change one thing and retest4. Try the lab5. Check & correct

01 / THINK → ACT → CHECK

Write the expectation first

“It doesn’t work” is hard to test. “At 20 cm the decision must be WAIT” is precise. Write input, expected result, actual result, and one proposed change. Start with the smallest repeatable failure.

double distanceCm = 20.0;
boolean expectedClear = false;
boolean actualClear = distanceCm >= 20.0;
System.out.println("Expected=" + expectedClear + ", actual=" + actualClear);

02 / THINK → ACT → CHECK

Test the boundary

If clear means strictly greater than 20, the boundary itself must wait. Test just below, at, and just above the boundary. That set catches a >= typo much more reliably than testing only a large distance.

double[] tests = {19.0, 20.0, 21.0};
for (double cm : tests) {
    boolean clear = cm > 20.0;
    System.out.println(cm + " -> " + clear);
}

03 / THINK → ACT → CHECK

Change one thing and retest

Logs should show what matters: input, units, state, and output. Fix the condition, then rerun all three inputs. A compile error means the code could not be built; a runtime error happens while it runs; a logic error can produce the wrong answer without throwing an exception.

System.out.println("distanceCm=" + distanceCm
    + ", state=" + state
    + ", motorOn=" + motorOn);
// Teaching fragment: these variables come from your routine.

04 / PREDICT → TEST

Your practice bench

Debugging lab

Goal: report CLEAR only when the measured distance is greater than 20 cm. Compare a buggy boundary with a corrected one. Include 19, 20, and 21 cm in your tests.

Predict the result before running.

Results will appear here.
  1. Run the buggy condition at 19, 20, and 21 cm. Record each result.
  2. Change only >= to >. Repeat all three tests.
  3. Explain which test exposed the bug and why the others did not.

05 / CHECK → CORRECT

Explain the evidence.

If the output looks right at 100 cm, is the boundary bug fixed?

Check your thinking & mentor notes

That test alone cannot distinguish > from >=. Both say clear at 100. Use an input where the two expressions differ: exactly 20.

Keep a builder’s notebook.

Write your prediction, result, and one change you tried. Explain why the result changed, using a measurement or trace.

Use the same evidence-based approach for repeated correction.
